## 1. 세 앱은 어떻게 하나

### Organic Maps — 트랙 기록 필터 (가장 정교함)
점 하나를 받을 때마다 아래를 **모두** 통과해야 트랙에 넣는다.

1. **속도 값이 없는 점은 버림** (`HasSpeed()` 없으면 skip). 예측기(Predictor)가 만든 가짜 점도 버림.
2. **정확도** 250m 초과면 버림 (Wi-Fi 위치까지 허용하는 느슨한 값 — 대신 아래 필터가 엄격).
3. **시간 역전·중복** (`dt <= 0`) 버림.
4. **최소 이동 10m** — *마지막으로 채택한 점*에서 10m 안이면 버림. 정지 중 흔들림(drift)이 거리로 쌓이지 않게 하는 핵심.
5. **정확도 원이 겹치면 버림** — 마지막 채택 점까지 거리가 그 점의 정확도(반경)보다 작고, 지금 점의 정확도가 그 절반보다 나쁘면 "같은 자리"로 본다.
6. **가속도 필터** — `(좌표로 계산한 속도 − 직전 보고 속도) / dt > 2 m/s²` 이면 점프로 보고 버림.
7. **방향·거리 예측** — 직전 두 점의 진행 방향과 지금 방향의 차이가 45°를 넘거나, 이동 거리가 예상(직전 구간 거리)의 2배(최소 10m)를 넘으면 버림.
8. 기록 종료 시, 마지막으로 받은 점이 채택되지 않았으면 **강제로 마지막 점을 추가**(도착 지점 누락 방지).

위치 요청: `PRIORITY_HIGH_ACCURACY` + **`setWaitForAccurateLocation(true)`**(첫 위치를 정확한 것이 올 때까지 기다림).

### OsmAnd — 단순 필터 + 분석 단계에서 "이동 시간" 분리
- 기록 간격: 자동차 프로필 3초, 자전거 5초. 정확도 50m 초과면 기록 안 함. 최소 거리·최소 속도 필터는 기본값 0(꺼짐).
- 같은 타임스탬프 위치는 무시. 일부 기기의 `Location.getTime()` 버그 때문에 **시스템 시각과 4주 넘게 차이 나면 시스템 시각을 사용**.
- 트랙 분석(`GpxTrackAnalysis`): **이동 시간·이동 거리**를 따로 계산. 두 점 사이 속도가 약 0.1m/s(0.36km/h)를 넘을 때만 "이동"으로 더함. 전체 시간과 별도로 보여줌.
- 신호가 끊긴 구간은 세그먼트로 나누고, "공백 포함 거리"와 "공백 제외 거리"를 둘 다 계산.
- 내비 중 터널에서는 경로를 따라 위치를 시뮬레이션(지도 데이터가 있어야 가능 — Ridemate엔 해당 없음).

### GPSLogger — 기록 앱다운 방어
- **오래된 캐시 위치** (`time <= 직전 점 time`) 버림.
- **비현실적 점프**: 두 점 사이 속도가 357m/s(약 1,285km/h)를 넘으면 버림 (아주 느슨한 안전망).
- 정확도 기준 미달이면 **일정 시간 재시도 → 시간 안에 가장 정확한 점을 채택**하는 방식도 지원.
- 최소 거리 필터(사용자 설정)로 정지 중 기록 억제.
- GPS 주차(week) 롤오버 버그가 있는 기기용 시각 보정.

## 3. Ridemate 적용 제안 (우선순위 순)

> 실주행 검증 결과(2026-09-30·10-05·10-06 출퇴근: 기록 3.0~3.2km vs 구글/경로 3.05~3.3km)로 보면 **현재 거리는 이미 꽤 정확**하다.
> 아래는 "가끔 생기는 튐"과 "긴 정차·터널" 같은 경계 상황을 막는 보강이다. 적용 전후를 같은 주행 로그로 비교해서 판단할 것.

### P1. 위치 점프 필터 강화 — 좌표 속도와 보고 속도 비교
- 지금은 좌표로 계산한 순간 속도가 300km/h 미만이면 거리에 그대로 더한다. 2초 사이 150m 점프(270km/h)도 통과한다.
- 제안: GPS가 보고한 속도(도플러, 훨씬 정확)가 있으면, **좌표 속도가 `보고 속도 × 1.5 + 15km/h`를 넘는 점은 거리에서 제외**. 보고 속도가 없으면 Organic Maps 방식의 **가속도 필터**(오토바이 기준 약 5m/s², 즉 18km/h/s — 급가속 판정값 12km/h/s보다 여유 있게).
- 제외한 점은 "마지막 정상 점"을 갱신하지 않는다(다음 정상 점에서 이어 붙임).
- 위험도 낮음, 효과: 도심 빌딩 반사(multipath)로 인한 순간 튐 차단.

### P2. 정지 중 흔들림이 거리로 쌓이지 않게
- 지금은 30m 이내 정확도면 서 있어도 점마다 몇 m씩 거리에 더해질 수 있다(신호 대기·주차장 출구 대기 3~7분).
- 제안(Organic Maps 방식 응용): **"마지막으로 거리에 반영한 점"을 기준점**으로 두고, 새 점까지 거리가 `max(10m, 두 점 정확도 중 큰 값)`보다 클 때만 거리에 더하고 기준점을 옮긴다. 보고 속도가 3km/h(정차 기준값과 동일) 이상이면 바로 반영.
- 실측 확인 방법: 주차장 대기 구간이 있는 출퇴근 기록에서 적용 전/후 거리 차이를 비교(디버그 빌드 `D.rides` 원시 좌표로 재계산 가능).

### P3. 시간 계산을 단조 시계로
- 구간 시간(`dt`)을 `loc.getTime()`(벽시계) 대신 **`loc.getElapsedRealtimeNanos()`** 차이로 계산. 기기 시각 변경·NTP 보정·일부 기기의 GPS 시각 버그(OsmAnd·GPSLogger가 따로 방어 코드를 둔 이유)에 영향받지 않는다.
- 기록에 저장하는 시각(시작/종료 표시용)은 지금처럼 벽시계 유지.
- iOS는 `CLLocation.timestamp`가 벽시계라 `ProcessInfo.systemUptime` 기준으로 받은 시각을 같이 저장하는 방식으로 대응.

### P4. 시작 시 정확한 첫 위치 기다리기
- `LocationRequest.Builder`에 **`setWaitForAccurateLocation(true)`** 한 줄(Organic Maps와 동일). 라이딩 시작 직후 대략적인 첫 위치(실내·지하 출발)에서 정상 위치로 뛰는 첫 구간 튐을 줄인다.
- 단, 지하주차장 출발이 일상이라 첫 위치가 늦게 올 수 있음 — 출발 대기 시간은 이미 정차 시간에서 제외되므로 영향 작음. 실기기 확인 필요.

### P5. 최고 속도는 "연속 2샘플 이상 유지"한 값으로
- 지금은 필터를 통과한 단일 샘플이 최고 속도가 된다. 과거 GPS 최고속도 오탐 이력이 있었다.
- 제안: 직전·현재 두 샘플의 **작은 값**을 최고 속도 후보로 사용(= 4초 이상 유지된 속도). 진짜 최고 속도는 거의 깎이지 않고, 단일 튐은 제거된다.

### P6. 신호 공백(터널·지하차도) 뒤 거리 보정 — 신중히
- 지금은 60초 넘는 공백 사이 거리를 버린다(과거 백그라운드 프로세스 킬로 거리가 폭증했던 버그 때문에 의도적으로 보수적).
- 제안: 공백이 60초~10분이고, 공백 앞뒤 직선거리 ÷ 공백 시간이 **그 라이딩의 평균 이동 속도 × 1.5 이하이면서 120km/h 이하**일 때만 직선거리를 더하고 `gpsGapBridgedCount`로 따로 센다(OsmAnd의 "공백 포함/제외 거리"를 하나로 합친 형태).
- 직선거리라 실제보다 짧게 잡히는 쪽(안전한 쪽)으로 틀린다. 프로세스 킬 복원 경로와 겹치지 않게 반드시 별도 플래그로 구분할 것.

### P7. 요약 화면에 "이동 시간" 표시 (기능 제안)
- OsmAnd처럼 **전체 시간 / 이동 시간**을 나눠 보여주면 평균 속도가 현실적으로 나온다(정차 포함 평균 10km/h → 이동 평균 20km/h 식).
- 이미 `stoppedMs`(정차 시간)를 수집하고 있어 `이동 시간 = 전체 − 출발 대기 − 정차`로 바로 계산 가능. 가혹 조건 판정 2단계 UI와 같이 다루면 자연스럽다.

## 3-1. 과거 실기기 교훈과의 충돌 (ridemate-dev 스킬 기록) — 적용 전 반드시 확인
- **"거리는 원시 좌표 델타로 항상 누적, 일시정지 상태로 거리를 껐다 켜지 말 것"** — 예전에 이동 확정 상태로 거리 누적을 막거나 소급 롤백하다 라이딩 거리가 0km로 사라진 사고가 두 번 있었다.
  → P2는 "상태"가 아니라 점 단위 기준점 방식이라 거리를 지우거나 되돌리지 않는다(최악의 경우 정차 1회당 10m 미만 누락). 그래도 같은 계열 위험이므로 **실주행 로그 재계산에서 거리 손실이 없는지 확인한 뒤에만** 적용.
- **"최고속도에 지속성 조건을 걸면 순간 최고속도를 놓쳤다, 단순 스파이크 필터가 실측과 더 잘 맞았다"**
  → P5는 이 교훈과 정면으로 부딪힌다. 로그로 실제 단일 튐이 확인될 때만 재검토하고, 기본은 **보류**.

## 4. 바꾸지 않아도 되는 것
- **정확도 30m 컷**: Organic Maps(250m)·OsmAnd(50m)보다 엄격하지만 오토바이 도심 주행엔 적절. 대신 P1·P2로 보완.
- **속도 튐 필터(초당 40km/h)·속도 정확도 3m/s 컷**: 세 앱보다 오히려 꼼꼼함. 유지.
- **2초 간격**: 배터리·정확도 균형상 적당(OsmAnd 자동차 3초).
- **칼만 필터 직접 구현**: Fused Location Provider가 이미 센서 융합·평활화를 하므로 앱에서 한 번 더 하면 지연만 늘어난다. Organic Maps·OsmAnd도 위치에는 별도 칼만을 쓰지 않는다(OsmAnd의 칼만은 나침반용).

## 5. 진행 방식 제안
1. ✅ 디버그 빌드 원시 GPS 로거: `GpsDebugLog.java`(RidingService, 라이딩마다 jsonl 파일). JS `_dbgLog`는 백그라운드에서 빠져서 네이티브로 구현. iOS(`RideTracker.swift`)는 아이폰 입수 후.
2. 출퇴근 3~5회 로그로 현재 로직 vs 개선안을 **같은 입력에 오프라인 재계산**해 비교(구글 지도 경로 거리와 대조) — `tools/gps-replay/replay.mjs`.
   가짜 데이터 시험(실제 1.6km + 3분 정차 흔들림 ±8m + 150m 튐 1회): current 2.277km / P1 1.951 / P2 1.838 / P1+P2 1.578km.
3. 차이가 의미 있으면 Java → Swift → JS 순으로 반영, 실주행 1회 확인 후 릴리즈.
